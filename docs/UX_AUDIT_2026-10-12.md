# EZCrop user-experience audit — October 12, 2026

**Recommendation:** preserve the small, single-image editor and make its output and interaction states more trustworthy. The normal crop-and-download path works well. The most useful next release would address invalid custom-size exports, export-state clarity, keyboard orientation, and short-screen usability before adding more editing features.

This was an audit and test task. Application source, dependencies, and the deployed site were not changed. Recommendations below are proposed work, not implemented repairs.

**Subsequent authorized work:** the user then approved implementation. This document remains the baseline record; the implemented changes and fresh verification are recorded in [the UX repair report](UX_REPAIRS_2026-10-12.md).

## Fixes to prioritize

### 1. Invalid custom dimensions still allow a download with different dimensions

**Priority: first. Confirmed in the development build, production build, and public site.**

Select Custom size, enter `8000` for width, leave the field, and click Export Image. The field remains `8000`, is marked invalid, and displays a validation message, but the download is still allowed. The observed file was `audit_800x600.webp`, decoded at **800×600**. A separate test with width `0` produced the same previous valid size.

The underlying dimension validation correctly prevents invalid values entering the export pipeline. The problem is that the interface still permits exporting while its visible input is invalid. A person can reasonably assume their edited dimensions apply to the downloaded file.

**Proposed change:** block export while the active Custom fields contain invalid drafts. Keep the last valid crop geometry, identify the field needing correction, and restore export immediately after a valid correction or selection of another mode. A valid edit followed directly by clicking Export must use the newly committed dimensions.

**Evidence:** [local screenshot](../output/playwright/ux-audit-2026-10-12/04-invalid-custom.png), [live screenshot](../output/playwright/ux-audit-2026-10-12/10-live-invalid-custom.png). Relevant code: `src/components/PresetPicker.tsx:98–119`, `src/components/Sidebar.tsx:83–86`.

### 2. Offline AVIF recovery is delayed in automated WebKit

**Priority: next. Reproduced in Playwright WebKit 26.5 on Windows; physical Safari is unverified.**

Load an image, set a 100×100 output, make the context offline before the AVIF assets have been used, select AVIF, and export. The original regression failed because no recovery alert appeared within 30 seconds. The configured AVIF worker timeout is 120 seconds, so that 30-second result alone did not establish failure of the encoder's deadline.

After verifying GitHub, a new probe retained UI state, alerts, download events, and image/worker events throughout the operation. **At 135.015 seconds it still showed Exporting…, with no alert or download.** Cancelling at that point returned to the upload screen in 198ms. The matching online 100×100 AVIF control succeeded within five seconds. Other tested engines passed the original offline recovery regression.

Instrumentation showed the source image loading successfully, followed by a blob resize worker that posted work and emitted an error without a response. The application's encoder worker was never created in the offline run. In the online control the resize worker responded, then the encoder worker ran and a download occurred. This strongly supports a stall in the preceding Pica resize stage, before the AVIF worker's deadline applies. It does not establish why that worker failed or prove physical Safari/iOS behavior.

**Proposed change:** investigate the resize-worker error path and ensure the complete export operation can recover from a failed stage. A bound on the complete operation is a possible safeguard; the exact fix should follow root-cause verification. Provide useful reconnect/JPEG/WebP guidance when appropriate. Reproduce on physical Safari before claiming a Safari-specific defect or repair. Cancellation remains responsive but currently discards the editing session.

**Evidence:** [new summary](../output/playwright/ux-recheck-2026-10-12/webkit-summary.md), [complete offline/online event record](../output/playwright/ux-recheck-2026-10-12/webkit-recheck.json), [offline endpoint screenshot](../output/playwright/ux-recheck-2026-10-12/webkit-offline-final.png), and [original follow-up](../output/playwright/ux-audit-2026-10-12/webkit-offline.json). Relevant code: `src/hooks/useExportPipeline.ts:189–206,407` and installed `node_modules/pica/index.js:240–265`. No speculative source fix was applied.

### 3. Settings can contradict a pending export

**Priority: next. Confirmed in the production build with a controlled eight-second worker delay.**

Start a 600×600 AVIF export, then select JPEG and Square Medium. The UI now shows **JPEG / 1000×1000 / Exporting…**, but the eventual download is **600×600 AVIF**. Export correctly retains its original settings; the interface does not communicate that snapshot.

There is also no app-level completion message after a successful download. The only way to abandon a slow export in the interface is Upload a different image, which also discards the current editing session. The browser may provide its own download notification; that is separate from app feedback.

**Proposed change:** display the pending job's captured settings prominently, such as “Exporting 600 × 600 AVIF; changes apply to your next export.” This preserves the existing ability to continue editing. Disabling controls during export is an alternative product choice, not a required correctness fix. Add a persistent status region and consider a Cancel export action that preserves the image and composition. Say “Download started” when appropriate rather than implying the app can verify the user's final disk location.

**Evidence:** [pending export screenshot](../output/playwright/ux-audit-2026-10-12/09-pending-export-mismatch.png). Relevant code: `src/App.tsx:53–65`, `src/components/Sidebar.tsx:60–76`, `src/components/ExportButton.tsx:13–41`, `src/hooks/useExportPipeline.ts:263–274`.

### 4. Keyboard users lose their place during screen changes

**Priority: next. Confirmed focus transitions and incorrect handle wording.**

After keyboard-focused upload, focus becomes `BODY`. Activating Upload a different image produces the same result. The new screen has no deliberate focus destination. Keyboard crop movement itself works, including the library's arrow-key handling.

The east Freeform handle announces “Use the up and down arrow keys,” but ArrowLeft changes its width. The dependency supplies similarly incorrect wording for the west handle.

**Proposed change:** move focus to a meaningful editor heading/region after upload and back to Upload image after reset. Override the east/west handle instructions with left/right wording. A small optional keyboard-help line would also improve discovery.

**Evidence:** `Keyboard focus after upload`, `Keyboard reset focus and portrait phone layout`, and `Freeform handle keyboard instructions` in the observations. Relevant code: `src/App.tsx:41–50`, `src/App.tsx:85–100`, `src/components/CropEditor.tsx:33`.

### 5. Light-mode upload errors need stronger contrast

**Priority: next. Measured in the rendered browser.**

An unsupported-file message renders at 12px with foreground RGB **251,44,54** on **250,250,250**, giving **3.65:1** contrast. Normal-size text has a **4.5:1** minimum under [WCAG 2.2's contrast criterion](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**Proposed change:** use the darker error styling already used for export/custom errors. Recheck both themes and retain the alert semantics. This is a specific measured contrast problem, not a claim about the application's overall WCAG conformance.

**Evidence:** [upload error screenshot](../output/playwright/ux-audit-2026-10-12/02-upload-error.png). Relevant code: `src/components/UploadZone.tsx:141`.

### 6. Short landscape screens cannot keep the crop and controls together

**Priority: next for mobile usability. Confirmed layout behavior.**

At **844×390**, the landscape preview occupied document y192–465 and Export began at y569. The page was 694px tall. Vertical centering inside the tall editor column wastes scarce space above the image, and the zoom/fit toolbar is below the initial viewport.

The fit control changes an image height cap rather than genuinely fitting the editor to the available viewport. On the portrait-source check at the same viewport, after reaching and activating the control, the page was at scroll position y304 and the preview remained partly above the visible screen. Browser automation scrolls offscreen controls into view, so this is not attributed to the button's event handler. The fit action itself does not bring the complete preview back into view.

**Proposed change:** make the preview and toolbar fit the available height on short screens, with top alignment where needed. Clarify or implement actual Fit width / Fit height behavior. Test portrait and landscape sources with the mobile browser's address bar present on a physical device before calling this complete.

**Evidence:** [844×390 layout](../output/playwright/ux-audit-2026-10-12/layout-844x390.png), [fit-height state](../output/playwright/ux-audit-2026-10-12/07-fit-height-landscape.png). These are full-page captures; the viewport was only 390px high. Relevant code: `src/components/CropEditor.tsx:28–48` and `src/components/Sidebar.tsx:59`.

## Improvements with the greatest user value

These are design opportunities, distinct from the confirmed problems above.

| Improvement | Observed reason | Smallest useful direction |
| --- | --- | --- |
| Show dimensions on presets | People see L/M/S, Tall/Mid/Short, and Wide/Mid/Narrow. Exact dimensions are in hover titles and accessible names. Touch users must select to discover them. | Make dimensions visible, or show a clear selected-preset description. Use “Landscape” and “Portrait” rather than Rect/Vert if space allows. |
| Add “Use entire image” and proportional resize | An 1800×1200 image starts as a 1200×1200 square selection. Entering Freeform correctly preserves that square; it does not restore the missing sides. | Add an explicit full-image/original-proportions action. Allow a user to type one dimension and keep the original ratio. Preserve existing mode behavior. |
| Warn about enlargement | A 320×240 image defaults to 1600×1600 output. Its square source crop contains only 240×240 pixels. | Show “Enlarging from 240 × 240; detail may look soft,” or offer a source-size starting option. Do not silently change established preset sizes. |
| Improve the phone workflow | At 390×844 with a portrait source, Export starts at y1195 and the document is 1356px tall. The crop is no longer visible when working near the bottom. There was no horizontal overflow. | Consider a compact sticky output/export strip and a less vertically spread settings panel. Treat normal scrolling as a tradeoff, not a failure by itself. |
| Enlarge touch hit areas | Range elements measure 6px high; theme/fit buttons measure 28/32px; replacement-image text is 16px high. Crop corner handles retain 24×24px touch targets. | Increase invisible padding for sliders and secondary actions while retaining the compact appearance. Dimensions alone do not establish effective browser hit areas or a blanket accessibility failure; see [target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). |
| Explain the tight-crop limit | Dragging a fixed-aspect corner inward stops at zoom 3×. A 630px displayed selection stopped at 210px. Freeform does not share this fixed-mode limit. | Explain the limit or permit tighter selections with an enlargement warning. This is an intentional source restriction, not a newly introduced geometry regression. |
| Show actual output quality and file size | Quality changes affect encoding but the canvas continues showing the source. A noisy 1600×1600 WebP was estimated at ~1.25 MB and downloaded at 2,045,288 bytes (~1.95 MiB); the estimate was roughly 36% below the actual size. A synthetic scene estimate was much closer: ~34.4 KB versus 34,254 bytes. | Keep the estimate clearly approximate. Display actual bytes after export, and consider an optional encoded preview for choosing quality. Do not promise a target upload limit based on the estimate. |
| Surface privacy before upload | At 1440×900, the privacy footer begins exactly at y900, below the initial screen. | Put “Images stay on your device” beside the file chooser, or include the footer within the initial viewport layout. |
| Explain format tradeoffs without hovering | “Compact; slower to encode” and other format hints are only in title attributes. GIF opens and exports without an in-editor warning that animation becomes a still image. TIFF failure has useful guidance. | Display a short selected-format hint, explain still-image export for animation, and make unsupported phone-image formats clearer. Keep the existing JPEG-transparency warning. |
| Preserve work while replacing an image | Upload a different image immediately clears the editor and crop before another file has been chosen. | Open the chooser while retaining the current edit; replace it only after a new image decodes successfully. A small Reset crop action would help recover from experimentation without re-uploading. |
| Honor reduced-motion preferences | With reduced motion enabled, computed styles still report the moving `marching-ants` selection border. | Use a static visible boundary under reduced motion, and review the export spinner. This is a comfort improvement rather than a claim that cropping is unusable. |

This audit does not establish a need for batch processing, accounts, cloud storage, or a large photo-editing toolset.

## What already works well

- The desktop layout presents a large crop preview and a consistently placed output panel. The interface is focused and visually coherent.
- Upload can be activated with keyboard Enter/Space. A synthetic drag-and-drop upload entered the editor successfully.
- All nine fixed presets, Custom, and Freeform were exercised. Output-size changes at the same ratio preserve composition; full-source bounds and independent Freeform resizing are covered by regressions.
- Valid custom boundaries are accepted and invalid values do not enter the underlying export state. The missing piece is preventing the contradictory export described in finding 1.
- Crop movement supports keyboard, mouse, and Chromium-emulated touch. No horizontal overflow appeared in the tested layout matrix down to 320 CSS pixels.
- Preset/format buttons expose their selected state, controls have useful accessible names, and focus outlines are visible. Output dimensions and estimates use live regions.
- Valid format downloads have real matching signatures, dimensions, and tested pixel/transparency behavior. JPEG's black transparency flattening is explicitly explained in the UI.
- Quality 60 and 100 were exercised for WebP, JPEG, and AVIF. All six outputs decoded at 600×600, and the higher quality produced larger files in each format for the test image. The saved dark-mode preference survived reload.
- A 7,680×7,680 JPEG from the synthetic landscape exported and decoded correctly at the requested dimensions (548,574 bytes). This demonstrates one upper-bound scenario, not every device's memory capacity.
- BMP input opened and exported; unsupported TIFF decoding in Chromium produced clear JPEG/PNG recovery guidance. Animated GIF input opened and exported as a still image.
- Local exploratory scenarios produced no page-level uncaught JavaScript errors.
- The public site produced a normal 600×600 WebP with the expected filename and decoded dimensions.

## Suggested order of work

1. **Trust, recovery, and accessibility:** invalid custom drafts, offline AVIF investigation, pending-export clarity, keyboard focus/instructions, and upload-error contrast. Add only targeted regression coverage for these reproduced cases.
2. **Everyday workflow:** short-screen preview behavior, visible preset dimensions, full-image/proportional resize, enlargement guidance, and a compact mobile export action.
3. **Comfort and confidence:** actual output feedback, a composition-preserving Cancel/Replace flow, reduced motion, and optional encoded preview.

Each step should be reviewed as a separate, bounded change. No redesign is needed to realize most of this value.

## Limits of this audit

- There was no physical iPhone/iPad/Android testing or manual VoiceOver/TalkBack/NVDA session. Automated WebKit is not physical Safari, and touch emulation is not a real phone.
- Layout/reflow checks included 320 CSS pixels, but do not prove every browser zoom, OS text-size, forced-colors, or assistive-technology combination.
- File-size and timing observations use controlled synthetic inputs. They are not a photographic quality study or reliable performance benchmark; browser suites ran alongside other audit work.
- One maximum-area JPEG completed. Sustained memory pressure, huge camera files on low-memory devices, and maximum-area AVIF were not stress-tested.
- The live site received a focused smoke check. No new release was published and no byte-for-byte production asset comparison was performed.
- Accessibility findings are specific observed barriers and source facts, not a certification or complete formal WCAG evaluation.
